# Constitution — prohibitions and conventions

Always loaded. Violating a prohibition fails review automatically. On any
conflict: this file, `definition-of-done.md`, accepted ADRs, and the
nearest `AGENTS.md` win over skills and agent playbooks.

## Prohibitions

- **No raw SQL** outside Drizzle. Exceptions: migrations generated by
  drizzle-kit, and foundation primitives explicitly approved by an ADR/spec
  because Drizzle cannot express them — each marked with a comment
  referencing that approval.
- **No DB access** outside action handlers, module services, or typed action
  target resolvers executed by core inside its transaction. Clients (mobile,
  web, AI) never touch the DB.
- **No `any`, no `as unknown as`**, no `@ts-ignore` / `@ts-expect-error`
  without a linked issue.
- **No new dependencies** without explicit human approval. Propose in the PR
  description first.
- **No changes to `packages/core`** within module implementation tasks. If
  core is missing something, stop and report — do not work around it.
- **No silent product forks.** A new capability, principal, owned table, or
  invariant that the Linear feature card did not name is a stop, not a
  drive-by. Mechanical contract detail (timeout/rate-limit defaults, a Zod
  refine a test proved, a CHECK the card implied) may land in the same PR
  and must be named in the description.
- **No workarounds for decisions.** Code that compensates for an ADR, a
  contract, or a schema shape instead of following it is a stop, not a fix
  (`AGENTS.md` → How we work).
- **Do not read, grep, or cite `docs/archive/`** unless the human names a
  file. Those novels are not a contract, a golden, or a pipeline. Use
  `docs/reference/` for v1 archaeology. Protocol manuals in `docs/specs/`
  change via ADR or a same-PR patch when a test proves them wrong.
- **No accepting `companyId` (or any tenant identifier) from action input**
  as an access grant.
- **No storing derived order state in chat messages** (or any projection).
  Store IDs, subscribe to events.
- **No secrets in code or logs.** Config through validated env
  (`packages/config`). Never read or print `.env`.
- **Never hand-edit generated files**: `packages/db/src/schema/auth.ts`
  (`pnpm --filter @showzy/api auth:generate`), `packages/contract/openapi.json`
  (`pnpm --filter @showzy/contract openapi:generate`),
  `apps/web/src/routeTree.gen.ts` (router plugin), generated drizzle SQL
  (`pnpm --filter @showzy/db db:generate`).
- **Never modify the v1 repository** (`E:\showzy`). It is read-only
  reference.
- **No comments in code.** Agents never add `//`, `/* */`, or JSDoc to
  `.ts`/`.tsx` files: a name, a type, a small function, or a test carries
  the meaning; the commit subject carries the ticket. The only permitted
  comment lines are the ones a rule requires — the approval reference on an
  ADR/spec-approved raw-SQL primitive, `eslint-disable` / `@ts-expect-error`
  with a linked issue, and `@vitest-environment`. A hook blocks the rest.
  Do not strip existing comments in lines you are not otherwise changing.
- **No prose artifacts.** Commit messages, PR bodies, Linear comments, and
  reports follow the output protocol in `CLAUDE.md`. A change that needs a
  page of explanation needs a smaller ticket or an ADR, not a longer commit.

## Conventions

- **Action naming**: `<module>.<verb>` (e.g. `orders.confirm`,
  `pricing.resolveProductPrice`). Verbs are imperative, camelCase.
- **Event naming**: `<module>.<pastVerb>` (e.g. `orders.created`). The
  payload schema version lives in the event envelope, never in the name.
- **Module structure** (`packages/modules/<name>/src/`):
  - `actions/<name>.contract.ts` — client-safe descriptor (ADR-0016); may
    import only Zod, `@showzy/core/contract`, and shared validation.
  - `actions/<name>.ts` — server implementation (`implementAction`), target
    resolver/confirmation summary, and handler.
  - `services/` — internal logic shared between actions of this module.
  - `events/` — emitted event definitions and subscriptions that bind
    consumed events to internal idempotent system actions; no arbitrary DB
    handler logic.
  - `index.ts` — exports **only** actions and events.
  - `index.contract.ts` — exports only client-safe action descriptors for
    `packages/contract`.
  - Owned tables live in `packages/db/src/schema/<module>.ts` (ADR-0014); a
    module imports only its own schema file.
- **Action metadata is mandatory**: `description`, `principal`, `transport`,
  `input`/`output` (Zod v4), `permissions`, `aiExposure`, `risk`,
  `requiresConfirmation`, `idempotent`, `emits`, `errors`, `audit`,
  `timeout`; conditional metadata/resolvers from `docs/specs/core.md` are
  mandatory when applicable.
- **Errors**: typed error classes from `@showzy/core/errors`. Never
  `throw new Error("...")` in domain code.
- **Validation**: Zod v4 schemas are the single source — form, API contract,
  AI tool, and DB boundary all derive from the same schema.
- **DB access**: Drizzle only, inside action handlers, module services, or
  typed target resolvers under the core transaction. Every table is owned by
  exactly one module (ADR-0014).
- **Tenant context**: scope comes from the verified action context, never
  from input as an access grant. Every action declares exactly one principal
  mode — `staff` | `customer` | `public` | `system` | `consumer` | `account`
  | `share` (ADR-0013, ADR-0018, ADR-0020, ADR-0022). Customer,
  single-target public, and share actions use typed target resolvers;
  public-global actions are read-only over a spec-declared published
  projection; system actions declare tenant/global scope; consumer actions
  are authenticated global read-only discovery without `companyId`; account
  actions are own-user-scoped pre-tenant operations without `companyId`;
  share actions are unauthenticated capability-token reads/writes.
- **Cross-module composition** (ADR-0015, ADR-0021): effects go through
  domain events (transactional outbox); synchronous reads go through
  `ctx.call` of another module's principal-compatible `risk: "read"` action;
  rare all-or-nothing writes use only spec-declared `ctx.callAtomic`
  capabilities; cross-cutting projections (`search`, `analytics`) use
  read-model grants declared in the owning spec. Direct imports of another module's services are
  forbidden.
- **Language**: all code, comments, commit messages, and docs in English.
  Talk to the human in the language they use.
- **Architectural decisions**: any deviation from `docs/blueprint.md` or an
  accepted ADR requires a new ADR (`docs/adr/template.md`) accepted by the
  human first.
